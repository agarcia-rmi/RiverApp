What you have today is the face of the app — every screen, flow, and interaction your members will touch. What this manual covers is the plumbing behind it: how a member signs in, where each piece of information lives in MinistryPlatform, and the exact steps to package and publish it.

Read it top to bottom for the full journey, or jump to a part from the bar above. Field names from MinistryPlatform appear as Table.[Column] chips so your developer can search for them directly. Nothing here requires throwing away the prototype — the production app is the same interface, wrapped for the stores and connected to live data.

01 The big picture

How the pieces fit togetherThree parts: the app, a small backend, and MinistryPlatform.

The prototype is a single web file that draws every screen and fills it with sample data. To go live, three things work together. Keeping them separate is what keeps members' giving and contact data safe.

The app (what members install)

Your existing interface, packaged in a thin native shell so it can live on the stores, send push notifications, store sermon notes on-device, and open the camera for check-in. It never holds passwords or platform keys.

The backend (the trusted middle)

A small service that holds the MinistryPlatform client secret, signs members in, and shapes data before it reaches the phone. This is the single most important rule of the build:

Non-negotiable

MinistryPlatform credentials never live in the app. Anything shipped to a phone can be read by anyone. The client secret, service-account login, and direct database access stay on the backend only.

MinistryPlatform (the source of truth)

Every member, household, gift, group, and event already lives here. The app reads and writes through MinistryPlatform's OAuth login and REST API — ideally through the custom Page Views and stored procedures your team already builds, rather than raw tables.

02 Who's signing in

Member login with MinistryPlatformOAuth 2.0 / OpenID Connect — the same sign-in your membership course already uses.

Members log in with their MinistryPlatform account. MinistryPlatform acts as the identity provider, so the app never sees or stores a password — it receives a short-lived token that proves who the person is and what they're allowed to see.

Set it up once in MinistryPlatform

  1. Register the app as an OAuth clientIn the MinistryPlatform OAuth/OIDC settings, create a client for the mobile app. You'll get a Client ID; the matching secret stays on the backend.
  2. Use Authorization Code with PKCEThis is the flow built for phones — it works safely without shipping a secret in the app. Turn on PKCE for the mobile client.
  3. Add redirect URIsRegister a custom scheme and/or universal link so the login hands control back to the app, e.g. com.revival.theriver://auth and https://mp.revival.com/app/auth.
  4. Request the right scopesSo the app can identify the member and read their data on their behalf.
scope  openid scope  offline_access scope  http://www.thinkministry.com/dataplatform/scopes/all

What happens when a member taps "Sign in"

  1. App opens the secure browserIt sends the member to the MinistryPlatform authorize endpoint with the Client ID, scopes, and a one-time PKCE challenge.
  2. Member logs in on MinistryPlatform's pageThey never type their password into your app — only into MinistryPlatform.
  3. MinistryPlatform redirects backIt returns an authorization code to the app's redirect URI.
  4. Code is exchanged for tokensThe app (with PKCE) trades the code for an ID token, an access token, and a refresh token.
  5. Tokens are stored securelyIn the iOS Keychain / Android Keystore — never in plain storage.
  6. Member is resolved to a recordThe access token is sent to the backend, which calls MinistryPlatform to map the login to a person.
authorize request
# Step 1 — send the member to MinistryPlatform
GET https://mp.revival.com/ministryplatformapi/oauth/connect/authorize
      ?client_id=river_church_app
      &response_type=code
      &scope=openid offline_access http://www.thinkministry.com/dataplatform/scopes/all
      &redirect_uri=com.revival.theriver://auth
      &code_challenge={pkce_challenge}
      &code_challenge_method=S256
token exchange
# Step 4 — trade the code for tokens (PKCE, no secret needed)
POST https://mp.revival.com/ministryplatformapi/oauth/connect/token
   grant_type=authorization_code
   code={returned_code}
   redirect_uri=com.revival.theriver://auth
   code_verifier={pkce_verifier}
Mapping login → person

The ID token identifies the MinistryPlatform user. The backend resolves that user to dp_Users.[User_ID] and then to their Contacts.[Contact_ID]. From that point on, every screen in the app is filtered to that member's household, giving, groups, and badge.

Keep them signed in

Use the refresh token to renew access quietly in the background so members aren't asked to log in every time. Offer a clear Sign out that deletes the stored tokens.

04 Getting it published

Shipping to the App Store & Google PlayWrap the existing web app with Capacitor, then submit to both stores.

Because the prototype is already a complete web app, the fastest honest path to both stores is Capacitor — a native shell that runs your web app and adds the native abilities it needs (push, camera, secure storage). You keep one codebase and ship to iOS and Android from it.

4.0 — Gather these first

  • Apple Developer Program — about $99/year, required to publish on the App Store.
  • Google Play Console — a one-time $25 registration.
  • App icon & splash screen in the River brand (navy & gold).
  • A privacy policy URL and a support URL — both stores require them.
  • Screenshots for each required device size.

4.1 — Wrap the web app with Capacitor

terminal
# from the project folder containing the web app
npm install @capacitor/core @capacitor/cli
npx cap init "River Church" com.revival.theriver

# point Capacitor at the folder with index.html, then add platforms
npx cap add ios
npx cap add android
npx cap copy

4.2 — Set the app's identity

  1. App ID & nameBundle/Application ID com.revival.theriver, display name "River Church" (with an RMI variant if you ship two).
  2. Version & build numbersStart at 1.0.0 (1); bump the build for every upload.
  3. Icons & splashGenerate every required size from one master asset and drop them into each platform.

4.3 — Add the native abilities

push  @capacitor/push-notifications secure  @capacitor/preferences links  @capacitor/browser deep-link  @capacitor/app camera  @capacitor/camera

These map directly to features already in the prototype: push for announcements, secure storage for sermon notes and tokens, the in-app browser for embeddable pages, deep links for the OAuth return, and the camera for QR check-in.

4.4 — iOS: build & submit

  1. Open in Xcodenpx cap open ios, then sign in with your Apple Developer team under Signing & Capabilities.
  2. Turn on capabilitiesPush Notifications and Associated Domains (for universal-link login).
  3. Create the App Store Connect listingName, subtitle, description, keywords, screenshots, support & privacy URLs.
  4. Fill the App Privacy labelsDeclare what you collect: contact info, financial info (giving), and identifiers. Be accurate — this is reviewed.
  5. Upload & test via TestFlightArchive in Xcode, upload, invite your staff to test on real phones.
  6. Submit for reviewApple typically reviews within a day or two.

4.5 — Android: build & submit

  1. Open in Android Studionpx cap open android and let Gradle sync.
  2. Create a signing keystoreGenerate it once and keep it safe — you need the same key for every future update.
  3. Build a signed App BundleProduce the .aab for upload.
  4. Create the Play Console listingTitle, description, graphics, screenshots, category (Lifestyle), and content rating.
  5. Complete the Data safety formThe Google equivalent of Apple's privacy labels — disclose contact and financial data.
  6. Release through Internal testing → ProductionTest with staff first, then roll out.
Review gotchas — read before submitting

Member testimonies are user content. Apple's rules require apps with user-posted content to filter objectionable material and give a way to report and block. Your moderation gate (Part 7) covers filtering; add report/block to be safe.

Account deletion is required. Both stores require an in-app way to request account/data deletion. Provide a clear path that signs the member out and submits a deletion request.

Giving stays in Pushpay. Charitable donations are allowed outside in-app purchase, so routing to Pushpay is fine — just present it as a donation, not a purchase of goods. Confirm the current Apple and Google donation rules at submission time, as store policies change.

4.6 — After launch

Content and web-app fixes can ship as over-the-air updates (e.g., Capacitor live updates) without a new store review. Changes to native code, permissions, or icons require a new build and review. Keep the version number moving so members always see "up to date."

05 The native layer

Turning prototype features into real powersWhat each simulated feature needs to become live.

Push notifications

Register the device on login, store its token against Contact_ID, and send through APNs (iOS) and FCM (Android), or a service like OneSignal. Because tokens are tied to people, you can target members only — for example, the member-badge prompt.

Sermon Notes

Stay on the device in secure storage, kept ~45 days with a clear deletion warning. They're personal and private — they never sync to MinistryPlatform unless you decide otherwise later.

Streaming & external links

Embeddable pages open in the in-app browser. Sites that block embedding — Stream, Suno, Pushpay, YouTube, Vimeo — open in the phone's browser instead. That's expected behavior, not a bug.

Liquid-glass theming

The glass refraction is a Chromium effect, so it shows fully on Android and falls back gracefully on iPhone (WebKit). A native build can use Apple's own material for the same feel on iOS.

06 What the church updates

Content your team keeps freshNo developer needed — staff update these directly.

Word of the Week

The Home bubble shows a weekly confession and a Bible verse from Sunday's service. Each week is a set of entries, and the app cycles through them across the days of that week:

  • 1 entry → shown all week.
  • 3 entries → rotate every couple of days.
  • 7 entries → a different one each day.

Staff open the record for the upcoming week, add the confession and verse (with reference), and save. It goes live at the start of that week — queue future weeks ahead of time. KJV is public domain; for other translations, supply the licensed text.

Leadership Principles

The carousel card shows one principle per day. The simplest storage is a single ordered list of 365 rows — Day_Of_Year from 1 to 365 — read by today's day number. Because it keys on day-of-year (not a specific year), the same list repeats annually with zero upkeep. Handle Feb 29 by reusing day 365.

07 Trust & safety

Moderation, privacy & data careProtecting your members and clearing store review.

Testimony moderation

Testimonies and soul reports are reviewed before anyone else sees them. The app submits them, but they remain hidden until a staff member approves them in MinistryPlatform.

The gate

Nothing displays publicly unless [Approved] = 1. Just as important: the app never shows a member whether their entry was approved, rejected, or featured. Approval status is staff-only — surfacing it would pressure and expose people who shared something tender.

Privacy & data safety

  • Sensitive by nature. Giving history and contact details are personal. Disclose them honestly in the App Store privacy labels and the Google Data safety form.
  • Least exposure. The backend returns only the signed-in member's data, and only the fields a screen needs.
  • Deletion on request. Provide an in-app path to request account and data deletion, as both stores require.
  • Secure tokens. Login tokens live in the Keychain / Keystore and are cleared on sign-out.
08 Where to begin

Known challenges & a first sprintAn honest look at the hard parts, and the order to tackle them.

The parts that take the most care

  • The backend is real work. The app is largely done; the trusted middle layer (login, data shaping, push) is the main build.
  • Store compliance. User content, account deletion, and donation rules each need a deliberate answer before submission.
  • Custom content tables. Device tokens, Word of the Week, and Leadership Principles need new tables or views in MinistryPlatform.

A sensible first sprint

  1. Stand up the backend & MinistryPlatform loginProve a member can sign in and the app resolves their Contact_ID.
  2. Wire the read-only screensProfile, household, badge, giving — through Page Views. These deliver value fast and carry low risk.
  3. Add the write actionsRequests, soul reports, group join, event registration.
  4. Wrap with Capacitor & ship to TestFlight / Internal testingGet it onto staff phones before polishing.
  5. Layer in push & submitAdd notifications, complete privacy forms, and release.
09 Before you submit

Launch checklistA quick pass to confirm you're ready for both stores.

  • Backend live — holds the MinistryPlatform secret; app holds none.
  • OAuth client registered in MinistryPlatform with PKCE and redirect URIs.
  • Member login resolves to Contact_ID and filters every screen.
  • Read screens wired — profile, household, badge, giving, events, groups.
  • Write actions wired — requests, souls, group join, registration.
  • Custom tables built — device tokens, Word of the Week, Leadership Principles.
  • Moderation gate verified — nothing public until [Approved] = 1.
  • Report & block available on member content.
  • Account deletion path present in-app.
  • Privacy policy & support URLs published.
  • App Store privacy labels and Google Data safety form completed.
  • Icons, splash & screenshots in the River brand, all sizes.
  • Tested on real devices via TestFlight and Internal testing.
Last word

Verify the current Apple App Store and Google Play policies the week you submit — store rules shift, and a five-minute check saves a rejected build. Everything else here is built to last.
